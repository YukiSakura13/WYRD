# ADR: Architectural Decision Record

## Как использовать

Этот файл хранит важные архитектурные и продуктово-технические решения.

Формат записи:

- ID
- дата
- статус
- контекст
- решение
- последствия

Статусы:

- `accepted`
- `proposed`
- `deprecated`
- `superseded`

---

## ADR-001

- Дата: 2026-04-05
- Статус: `accepted`
- Тема: Базовый стек проекта

### Контекст

Проект уже реализован как лёгкий статический сайт/PWA без сборщика и без фреймворка.

### Решение

Сохраняем текущий стек как базовый:

- `HTML`
- `CSS`
- `Vanilla JS` через ES modules
- `localStorage`
- `PWA`

### Последствия

- проще поддерживать текущую кодовую базу
- быстрее делать небольшие продуктовые изменения
- нужно строже следить за дисциплиной модулей и документации

## ADR-002

- Дата: 2026-04-05
- Статус: `accepted`
- Тема: Документация как часть разработки

### Контекст

Нужно выстроить более плотную совместную работу с Codex, чтобы изменения опирались не только на код, но и на общий проектный контекст.

### Решение

Вводим обязательный набор опорных документов:

- `ARCHITECTURE.md`
- `docs/PROJECT_BRIEF.md`
- `docs/ROADMAP.md`
- `docs/FEATURES.md`
- `docs/CONTENT_MODEL.md`
- `docs/ADR.md`
- `docs/WORKFLOW_WITH_CODEX.md`

### Последствия

- у проекта появляется единый описанный контекст
- проще ставить задачи и отслеживать изменения
- документацию нужно обновлять регулярно, иначе она потеряет ценность

## ADR-003

- Дата: 2026-04-05
- Статус: `accepted`
- Тема: `ARCHITECTURE.md` как главный источник истины по структуре

### Контекст

Нужно, чтобы любые будущие изменения структуры сайта можно было быстро сверять с понятным документом.

### Решение

Главным архитектурным источником истины по текущей структуре считается:

- [../ARCHITECTURE.md](../ARCHITECTURE.md)

### Последствия

- рефакторинги и новые сценарии проще обсуждать до кода
- архитектурные изменения должны сопровождаться обновлением документа

## ADR-004

- Дата: 2026-07-18
- Статус: `accepted`
- Тема: Нативные UI-примитивы вместо React-зависимостей

### Контекст

Внешние проекты `Sonner` и `Vaul` дают полезные паттерны уведомлений, модальных окон и draggable sheet, но распространяются как React-компоненты. `WYRD` остаётся статическим PWA на HTML, CSS и ES modules.

### Решение

- не добавлять `React`, `Sonner` или `Vaul` в runtime
- перенести только необходимые interaction-контракты в небольшие нативные модули проекта
- использовать единый контроллер для modal/sheet: фокус, `inert`, Escape, восстановление scroll position, `visualViewport` и завершение закрытия по реальному `transitionend`
- применять drag-to-dismiss только к явно обозначенной ручке листа истории, с `10px` direction lock, отменой горизонтального намерения и ограниченным сопротивлением вверх
- использовать единый нативный центр кратких уведомлений, атомарно обновлять одинаковый ID и сохранять контекстные ошибки рядом с действием
- оставлять live-region семантику на самом уведомлении: polite `status` для info/success и assertive `alert` для error
- в reduced motion убирать пространственное перемещение, но сохранять видимое `140ms` opacity-состояние
- устанавливать выбранные материалы из `emilkowalski/skills` только как инструменты разработки, отдельно от runtime приложения

### Последствия

- сохраняются текущий стек, малый вес и отсутствие сборщика
- accessibility-поведение оверлеев становится единым и проверяемым
- внешние идеи проходят через визуальные и продуктовые правила `WYRD`, а не копируются как готовые компоненты
- новые modal/sheet и уведомления должны переиспользовать эти примитивы
